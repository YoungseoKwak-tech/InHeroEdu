# 0. 왜 프로젝트인가 — 입학사정관의 시선

```
일반 학생 원서:   클럽 3개 + 봉사 + 올림피아드 = "잘 따라함"
Builder 학생 원서: "저는 이걸 만들었습니다" = "얘는 다르다"
```

**사정관이 실제로 찾는 것**
- Activity list에 **직접 만든 것(Initiated)**이 있는가?
- "왜 그걸 했나"의 증거 → **존재하는 산출물(artifact)**
- 실패를 겪고도 **끝까지 완성**했는가?

🎓 **Ivy Tip**: Princeton AO의 실제 말 — "We don't want to see a list of clubs. We want to see what you *built* with your ideas." 하나의 완성 프로젝트가 다섯 개 클럽을 이긴다.

# 강의 70 · 좋은 프로젝트란

**원리: 3가지 교집합**

```
        [내가 신경 쓰는 문제]
               ╲
                ●  ← 좋은 프로젝트
               ╱
[내가 가진 역량] ─── [실제로 만들 수 있는 크기]
```

- **신경 쓰는 문제** 없이 시작하면 → 3개월 후 동기 소멸
- **역량 밖** 프로젝트 → 끝을 못 봄 (미완성 = 원서에 못 씀)
- **너무 크게** 잡으면 → 산출물 0개

---

# 70-1. 좋은 프로젝트 기준표

**자가 평가: 각 항목 1–3점, 18점↑이면 진행 적합**

| 기준 | 1점 | 2점 | 3점 |
|---|---|---|---|
| **문제 실재성** | 내가 가정한 문제 | 주변 사람이 겪는 문제 | 데이터/뉴스로 확인된 문제 |
| **산출물 명확성** | "무언가 만들 것" | 결과물 형태는 앎 | 결과물 + 성공 기준 명확 |
| **6개월 완성 가능** | 1년+ 필요 | 6–9개월 | 4–6개월 이내 |
| **내 역량 활용** | 새 기술 100% 필요 | 새 기술 50% 이내 | 기존 강점 60%+ 활용 |
| **차별점** | 기존 앱/단체와 동일 | 대상·방식 하나 다름 | 접근법이 명확히 독창적 |
| **에세이 연결** | 서사와 무관 | 느슨하게 연결 | 스파이크 서사와 직결 |

→ **18점 이상**: 설계 진행 · **12–17점**: 기준 하나 수정 후 재평가 · **12점 미만**: 아이디어 재선정

# 70-3. 흔한 실수 ❌ + FAQ

**❌ 흔한 실수**
- "AI 앱 만들겠다" → 산출물이 뭔지 모른 채 시작 → 미완성
- 교수님께 부탁해서 **이름만 올린 연구** → 에세이에서 들통
- 경진대회 수상을 목표로 잡음 → 수상 못 하면 프로젝트 전체 실패 취급
- **규모가 클수록 좋다**는 착각 → 사정관은 임팩트의 깊이를 본다

**Q. 이미 있는 앱/프로그램과 비슷하면 안 되나?**
A. 괜찮다. **"이미 있지만 우리 지역·언어·대상에는 없었다"** 가 충분한 차별점.

**Q. 팀 프로젝트 vs 개인 프로젝트?**
A. 팀도 OK. 단, 에세이에서 **"내가 어떤 결정을 내렸는가"** 를 명확히 써야 한다.

# 강의 71 · 아이디어 발굴 프레임워크

**원리: 좋은 아이디어는 '검색'이 아니라 '마찰(friction)'에서 나온다**

```
마찰 포인트 발굴 → 문제 정의 → 해결 가능성 필터 → 아이디어 후보 3개 → 1개 선택
```

**3가지 마찰 발굴 렌즈**

| 렌즈 | 질문 |
|---|---|
| **불편함** | 내가 매일 겪는 불편함 중, "이게 왜 아직도 이래?" 싶은 것? |
| **공백** | 내 학교·동네·커뮤니티에 "이게 없다"고 느끼는 것? |
| **분노** | 뉴스를 보다 "말도 안 돼, 내가 고치고 싶다" 싶었던 순간? |

---

# 71-1. 아이디어 발굴 — 4단계 프로세스

```
STEP 1: 마찰 목록 (10개)
   내가 겪은 불편·공백·분노를 구체적 장면으로 10개 쓰기

STEP 2: 문제 정의 (3개)
   10개 중 가장 자주 떠오른 3개 → "누가, 어떤 상황에서, 왜 힘든가" 한 문장

STEP 3: 해결 가능성 필터
   각 문제에 대해 → "6개월 안에 내 역량으로 prototype 가능한가?" YES/NO

STEP 4: 아이디어 선택
   YES 중 기준표 점수 가장 높은 1개 → 최종 선택
```

✍️ **실습**: STEP 1 지금 바로 시작 — 10분 안에 10개 써라. 생각하지 말고 쏟아라.

---

# 71-2. 아이디어 발굴 — 📝 채워진 예시

**학생 배경**: 한국 국제학생, 수학·코딩 강점, 이민 경험

| STEP 1 마찰 (발췌) | STEP 2 문제 정의 | 가능? |
|---|---|---|
| 미국 세금 신고 너무 복잡함 | 이민 1세대 가정이 무료 세무 도움 못 받음 | YES |
| AP 자료가 한국어로 없음 | 한국 유학생들이 AP 시험 준비 자료 접근 어려움 | YES |
| 학교 수질 냄새 이상 | 우리 지역 수질 데이터가 공개 안 됨 | NO (장비) |
| 멘토 구하기 너무 어려움 | 국제학생이 미국 대입 멘토 찾을 채널 없음 | YES |

→ **기준표 점수 최고**: "국제학생 대입 멘토 매칭 플랫폼 MVP" 선택

🎓 **Ivy Tip**: Harvard 합격생 다수가 "내 문제를 내가 풀었다"는 서사. 타인의 문제보다 **본인이 직접 겪은 문제**가 에세이 진정성에서 3배 강하다.

---

# 71-3. 흔한 실수 ❌ + Ivy Tip

**❌ 흔한 실수**
- 구글에서 "좋은 프로젝트 아이디어" 검색해서 따라함 → 에세이에서 진정성 0
- "사회적으로 좋아 보이는" 주제 억지로 선택 → 6개월 버티기 불가
- 아이디어 선택에 3주씩 씀 → **선택 1주 이내, 실행에 시간 써라**

**Q. 아이디어가 너무 작고 평범해 보여요.**
A. 작아도 된다. **"학교 도서관 신간 추천 뉴스레터"** 로 시작해서 구독자 300명 모으면, 그게 Columbia 에세이 메인 소재가 된 사례 있다.

**Q. 기술적 프로젝트여야 하나요?**
A. 아니다. 글쓰기, 음악, 커뮤니티 조직도 전부 유효하다. 핵심은 **완성된 산출물**.

# 강의 72 · 프로젝트 설계 캔버스

**원리: 캔버스 없이 시작 = 3개월 뒤 "방향을 잃었다"**

```
프로젝트 설계 캔버스 = 4개 블록
┌──────────────┬──────────────┐
│  목표 (Goal) │  범위 (Scope)│
├──────────────┼──────────────┤
│ 일정(Timeline│ 산출물(Output│
└──────────────┴──────────────┘
```

각 블록을 1페이지 이내로 **먼저 채운 후** 실행 시작.

---

# 72-1. 캔버스 블록 1 · 목표 (Goal)

**좋은 목표의 조건 — SMART+W**

| 요소 | 설명 | 예시 |
|---|---|---|
| **S** pecific | 구체적 | "앱을 만든다" → "iOS 앱 v1 출시" |
| **M** easurable | 측정 가능 | "사람들이 쓴다" → "월 50 active users" |
| **A** chievable | 현실적 | 6개월 내 달성 가능 |
| **R** elevant | 스파이크와 연결 | 입시 서사와 연관 |
| **T** ime-bound | 기한 명확 | "2025년 3월 31일까지" |
| **W** hy | 내적 이유 | "이게 왜 나에게 중요한가" 1문장 |

✍️ **실습**: 내 프로젝트 목표를 SMART+W로 작성.

---

# 72-2. 캔버스 블록 2 · 범위 (Scope)

**핵심 개념: MVP (Minimum Viable Product / Minimum Viable Project)**

```
처음 생각한 범위 (WANT)
  ├─ 앱: iOS + Android + 웹
  ├─ 기능: 매칭 + 채팅 + 결제 + 리뷰
  └─ 사용자: 전국 고등학생

MVP 범위 (NEED to finish)
  ├─ 플랫폼: 웹 only (Notion/Airtable 기반)
  ├─ 기능: 프로필 등록 + 이메일 연결
  └─ 사용자: 학교 국제학생 30명 파일럿
```

🎓 **Ivy Tip**: Stanford d.school 교수가 말한 "Scope it down until it's embarrassingly small — then ship it." 작게 완성하는 게 크게 미완성보다 100배 낫다.

---

# 72-3. 캔버스 블록 3 · 일정 (Timeline)

**6개월 기본 프레임**

| 단계 | 기간 | 핵심 활동 | 체크포인트 |
|---|---|---|---|
| **리서치** | M1 | 문제 인터뷰 5명+, 시장 조사 | 인터뷰 노트 |
| **설계** | M1–M2 | 와이어프레임/기획서 | 설계 문서 v1 |

| **개선** | M5 | 버그 수정·기능 보완 | v1.1 |
| **런칭·공개** | M6 | 공개 배포·발표·문서화 | 산출물 완성 |

# 72-4. 캔버스 블록 4 · 산출물 (Output)

**산출물 = "원서 마감일에 링크/파일로 첨부할 수 있는 것"**

| 프로젝트 유형 | 산출물 예시 |
|---|---|
| 소프트웨어 | GitHub repo + 배포 URL + 사용자 수 스크린샷 |
| 연구 | 논문 초고 + 데이터셋 + 발표 슬라이드 |
| 비영리 | 웹사이트 + 참가자 명단 + 이벤트 사진 |
| 미디어 | 발행된 매거진/뉴스레터 아카이브 링크 |
| 커뮤니티 | 멤버 수 + 미팅 로그 + 임팩트 요약 1장 |

✍️ **실습**: 내 프로젝트의 산출물 3개를 지금 적어라. 원서에 첨부할 링크를 상상하며.

# 강의 73 · 실행 계획

**원리: 계획 없는 실행 = 3개월 후 "어디까지 했더라?"**

```
실행 계획 = 마일스톤 + 주간 액션 + 간트 초안
```

**마일스톤 정의**
- 마일스톤 = **"멈춰 서서 확인하는 체크포인트"**
- 월 1회, 총 6개 (시작 + 중간 4 + 완성)
- 각 마일스톤에 **명확한 완료 기준(Done Criteria)** 필요

---

# 73-1. 마일스톤 설계 — 6단계 템플릿

| 마일스톤 | 시점 | 완료 기준 (Done Criteria) | 산출물 |
|---|---|---|---|
| **M0** 킥오프 | Week 1 | 캔버스 완성, 팀/멘토 확정 | 캔버스 1장 |

# 73-3. 주간 액션 루프

**"프로젝트는 주간 루프로 산다"**

```
매주 일요일 밤 (30분)
  ┌─ 지난 주 체크: 계획 vs 실제 → 갭 파악
  ├─ 이번 주 액션 3개: "화요일까지 A, 목요일까지 B, 금요일까지 C"
  └─ 블로커 1개: 막히는 것 → 멘토/팀원에게 월요일 질문
```

| 주간 루프 항목 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 목표 | "코딩 열심히 한다" | "로그인 기능 구현 완료" |
| 시간 | "될 때 한다" | "화·목 8–10pm 고정" |
| 블로커 | 혼자 며칠 고민 | 48시간 내 도움 요청 |

🎓 **Ivy Tip**: Yale 합격생의 말 — "주간 루프 없으면 6개월이 눈 깜짝할 새 지나간다. 30분 리뷰가 프로젝트를 살렸다."

# 73-5. 흔한 실수 ❌ + FAQ

**❌ 흔한 실수**
- 월간 계획 세우고 **주간 루프 없음** → 한 달 뒤 아무것도 안 됨
- Done Criteria 없음 → "어느 정도 됐나?"를 스스로 모름
- 간트를 한 번 세우고 **업데이트 안 함** → 현실과 괴리
- 프로젝트와 학교 시험이 겹칠 때 **둘 다 포기** → 시험 기간엔 액션 하나로 줄이고 유지

**Q. 계획이 자꾸 바뀌면 어떡하나요?**
A. 정상이다. 계획을 **"맞추는 것"** 이 목표가 아니라, **"어긋난 이유를 파악하고 재조정"** 하는 것이 목표다. 매주 루프에서 갱신하면 된다.

**Q. 혼자 하는데 멘토가 없으면?**
A. InHero 멘토 세션 + 같은 프로젝트 하는 서클 멤버를 "가짜 팀장"으로 삼아 주간 체크인하라.
