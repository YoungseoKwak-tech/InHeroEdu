# 0. 왜 프로젝트인가 — 입학사정관의 시선

```
일반 학생 원서:   클럽 3개 + 봉사 + 올림피아드 = "잘 따라함"
Builder 학생 원서: "저는 이걸 만들었습니다" = "얘는 다르다"
```

**사정관이 실제로 찾는 것**
- Activity list에 **직접 만든 것(Initiated)**이 있는가?
- "왜 그걸 했나"의 증거 → **존재하는 산출물(artifact)**
- 실패를 겪고도 **끝까지 완성**했는가?

🎓 **Ivy Tip 1**: Princeton AO의 실제 말 — "We don't want to see a list of clubs. We want to see what you *built* with your ideas." 하나의 완성 프로젝트가 다섯 개 클럽을 이긴다.

🎓 **Ivy Tip 2**: Harvard 입학처 데이터(공개 인터뷰 기반) — 2023년 합격자 상위 20%는 Activity list 1~2번 슬롯에 **스스로 창시한 프로젝트**를 올렸다. 참여(Participated)와 주도(Initiated)의 차이가 당락을 가른다.

🎓 **Ivy Tip 3**: Columbia 합격생 박지현(서울 국제학교 졸업, '24) 말 — "에세이 10개 중 6개가 프로젝트 하나에서 나왔다. 활동이 많은 게 아니라 깊이가 있어야 쓸 말이 생긴다."

# 강의 70 · 좋은 프로젝트란

**원리: 3가지 교집합**

```
        [내가 신경 쓰는 문제]
               ╲
                ●  ← 좋은 프로젝트
               ╱
[내가 가진 역량] ─── [실제로 만들 수 있는 크기]
```

- **신경 쓰는 문제** 없이 시작하면 → 3개월 후 동기 소멸
- **역량 밖** 프로젝트 → 끝을 못 봄 (미완성 = 원서에 못 씀)
- **너무 크게** 잡으면 → 산출물 0개

🎓 **Ivy Tip**: 교집합 확인 기준 — "이 문제를 주말 밤 11시에도 생각하고 있나?" YES면 신경 쓰는 문제다. NO면 다른 문제를 찾아라.

# 70-1. 좋은 프로젝트 기준표

**자가 평가: 각 항목 1–3점, 18점↑이면 진행 적합**

| 기준 | 1점 | 2점 | 3점 |
|---|---|---|---|
| **문제 실재성** | 내가 가정한 문제 | 주변 사람이 겪는 문제 | 데이터/뉴스로 확인된 문제 |
| **산출물 명확성** | "무언가 만들 것" | 결과물 형태는 앎 | 결과물 + 성공 기준 명확 |
| **6개월 완성 가능** | 1년+ 필요 | 6–9개월 | 4–6개월 이내 |
| **내 역량 활용** | 새 기술 100% 필요 | 새 기술 50% 이내 | 기존 강점 60%+ 활용 |
| **차별점** | 기존 앱/단체와 동일 | 대상·방식 하나 다름 | 접근법이 명확히 독창적 |
| **에세이 연결** | 서사와 무관 | 느슨하게 연결 | 스파이크 서사와 직결 |

→ **18점 이상**: 설계 진행 · **12–17점**: 기준 하나 수정 후 재평가 · **12점 미만**: 아이디어 재선정

---

# 70-2. 📂 실물 — 합격생의 프로젝트 유형별 분류

| 유형 | 예시 | 학교 |
|---|---|---|
| 소프트웨어 도구 | 시각장애 학생용 수학 점자 변환기 | MIT '24 |
| 비영리/캠페인 | 지역 이민자 가정 무료 법률 상담 플랫폼 | Yale '25 |
| 연구 논문 | 고등학생 대기오염 센서 네트워크 구축 | Princeton '24 |
| 미디어/출판 | 지역 청소년 작가 매거진 창간 (8호 발행) | Columbia '25 |
| 하드웨어/메이커 | 학교 수질 모니터링 IoT 기기 | Cornell '24 |
| 커뮤니티 조직 | 한국 청소년 멘토링 네트워크 (200명+) | Brown '25 |

🎓 **Ivy Tip 1**: 유형보다 **완성**이 중요하다. 미완성 MIT급 프로젝트 < 완성된 지역 커뮤니티 앱.

🎓 **Ivy Tip 2**: "소프트웨어 프로젝트는 코딩 못하면 못 해요"는 오해다. Glide, Bubble, Webflow 같은 노코드 툴로 Yale '25 합격생은 법률 상담 플랫폼을 코드 한 줄 없이 만들었다. 핵심은 **문제 해결 논리**이지 언어가 아니다.

🎓 **Ivy Tip 3**: 국제학생 특화 각도 — "한국/아시아 커뮤니티에 이 솔루션이 없다"는 맥락 자체가 차별점이다. 사정관 입장에서 지역 공백을 채우는 프로젝트는 글로벌 임팩트 서사로 읽힌다.

# 70-3. 🎓 실전 꿀팁 모음 (강의 70)

- **팁 1 — "이미 있다"는 함정 피하기**: Google에서 비슷한 앱이 검색된다고 포기하지 마라. "우리 학교/지역/언어권에 없다"가 충분한 차별점. Cornell '24 합격생은 이미 존재하는 수질 모니터링 기기를 **학교 예산으로 직접 제작·설치**해 로컬 임팩트를 만들었다.
- **팁 2 — 기준표 숫자를 믿어라**: 주관적 감으로 "이 아이디어 좋아 보여"보다 기준표 18점+이 훨씬 신뢰 가능한 필터다. 3개월 뒤 동기가 사라질 때 기준표가 당신을 붙잡는다.
- **팁 3 — 팀 프로젝트 역할 문서화**: 팀 프로젝트라면 Day 1에 "나는 어떤 결정을 내렸는가"를 Notion에 로그로 남겨라. 에세이에서 팀 프로젝트의 내 역할을 증명할 수 있어야 한다.
- **팁 4 — 미완성은 원서에 쓰지 마라**: Activity list에 "진행 중" 프로젝트를 올리면 사정관은 "아직 결과가 없다"로 읽는다. 완성 산출물이 있는 것만 1번 슬롯에 올려라.
- **팁 5 — 경진대회 수상 목표 금지**: 수상을 목표로 잡으면 수상 못할 경우 프로젝트 전체가 실패로 느껴진다. 목표는 **완성된 산출물**이고, 수상은 보너스다.
- **팁 6 — 교수 이름 빌리기 함정**: 교수님 랩에서 인턴십하며 이름만 올린 논문은 에세이 인터뷰에서 들통난다. "당신이 직접 내린 결정이 뭔가요?" 질문에 답하지 못하면 역효과다.

# 강의 71 · 아이디어 발굴 프레임워크

**원리: 좋은 아이디어는 '검색'이 아니라 '마찰(friction)'에서 나온다**

```
마찰 포인트 발굴 → 문제 정의 → 해결 가능성 필터 → 아이디어 후보 3개 → 1개 선택
```

**3가지 마찰 발굴 렌즈**

| 렌즈 | 질문 |
|---|---|
| **불편함** | 내가 매일 겪는 불편함 중, "이게 왜 아직도 이래?" 싶은 것? |
| **공백** | 내 학교·동네·커뮤니티에 "이게 없다"고 느끼는 것? |
| **분노** | 뉴스를 보다 "말도 안 돼, 내가 고치고 싶다" 싶었던 순간? |

🎓 **Ivy Tip**: Harvard 합격생 다수가 "내 문제를 내가 풀었다"는 서사를 썼다. 마찰 발굴은 **15분 타이머를 켜고 멈추지 않고** 써야 한다. 검열하지 마라.

---

# 71-1. 아이디어 발굴 — 4단계 프로세스

```
STEP 1: 마찰 목록 (10개)
   내가 겪은 불편·공백·분노를 구체적 장면으로 10개 쓰기

STEP 2: 문제 정의 (3개)
   10개 중 가장 자주 떠오른 3개 → "누가, 어떤 상황에서, 왜 힘든가" 한 문장

STEP 3: 해결 가능성 필터
   각 문제에 대해 → "6개월 안에 내 역량으로 prototype 가능한가?" YES/NO

STEP 4: 아이디어 선택
   YES 중 기준표 점수 가장 높은 1개 → 최종 선택
```

✍️ **실습**: STEP 1 지금 바로 시작 — 10분 안에 10개 써라. 생각하지 말고 쏟아라.

---

# 71-2. 아이디어 발굴 — 📝 채워진 예시

**학생 배경**: 한국 국제학생, 수학·코딩 강점, 이민 경험

| STEP 1 마찰 (발췌) | STEP 2 문제 정의 | 가능? |
|---|---|---|
| 미국 세금 신고 너무 복잡함 | 이민 1세대 가정이 무료 세무 도움 못 받음 | YES |
| AP 자료가 한국어로 없음 | 한국 유학생들이 AP 시험 준비 자료 접근 어려움 | YES |
| 학교 수질 냄새 이상 | 우리 지역 수질 데이터가 공개 안 됨 | NO (장비) |
| 멘토 구하기 너무 어려움 | 국제학생이 미국 대입 멘토 찾을 채널 없음 | YES |

→ **기준표 점수 최고**: "국제학생 대입 멘토 매칭 플랫폼 MVP" 선택

# 71-3. 아이디어 발굴 — 실전 툴킷

**실제로 쓸 수 있는 도구 목록**

| 도구 | 용도 | 무료? |
|---|---|---|
| **Notion** | 마찰 목록·아이디어 후보 정리 | ✅ |
| **Google Forms** | 문제 검증용 설문 5분 제작 | ✅ |
| **Reddit / Quora** | "내 문제와 같은 문제 겪는 사람이 있나?" 검색 | ✅ |
| **Answer The Public** | 키워드 관련 실제 사람들의 질문 파악 | ✅ |
| **Product Hunt** | 비슷한 솔루션이 이미 존재하는지 확인 | ✅ |
| **Calendly** | 인터뷰 섭외 링크 (멘토·학생 모두 활용) | ✅ |

🎓 **Ivy Tip 1**: Reddit r/teenagers, r/ApplyingToCollege에서 "내 문제와 같은 문제"를 검색하면 문제의 실재성을 10분 내 검증할 수 있다. Brown '25 합격생이 실제로 쓴 방법이다.

🎓 **Ivy Tip 2**: Product Hunt에서 비슷한 앱을 찾으면 "이미 있다"가 아니라 "이 앱이 왜 내 대상에게는 안 통하는가"를 분석하라. 그 갭이 차별점이 된다.

# 71-4. 흔한 실수 ❌ + Ivy Tip

**❌ 흔한 실수**
- 구글에서 "좋은 프로젝트 아이디어" 검색해서 따라함 → 에세이에서 진정성 0
- "사회적으로 좋아 보이는" 주제 억지로 선택 → 6개월 버티기 불가
- 아이디어 선택에 3주씩 씀 → **선택 1주 이내, 실행에 시간 써라**

🎓 **Ivy Tip**: Yale 입학 담당자 공개 발언 — "우리는 세상을 구하려는 지원자가 아니라 실제로 뭔가를 만든 지원자를 원한다." 거창한 아이디어 1개보다 작게 완성한 프로젝트 1개가 낫다.

**Q. 아이디어가 너무 작고 평범해 보여요.**
A. 작아도 된다. **"학교 도서관 신간 추천 뉴스레터"** 로 시작해서 구독자 300명 모으면, 그게 Columbia 에세이 메인 소재가 된 사례 있다.

**Q. 기술적 프로젝트여야 하나요?**
A. 아니다. 글쓰기, 음악, 커뮤니티 조직도 전부 유효하다. 핵심은 **완성된 산출물**.

# 71-5. 🎓 실전 꿀팁 모음 (강의 71)

- **팁 1 — 마찰 목록은 종이에 손으로 써라**: 디지털 도구는 검색·수정 유혹이 생긴다. 종이에 15분 타이머 놓고 10개를 써야 검열 없이 솔직한 마찰이 나온다.
- **팁 2 — "이미 있는 솔루션" 찾기**: Product Hunt에서 비슷한 제품을 찾아 1-star 리뷰를 읽어라. 그 불만이 내 차별점의 힌트다. Princeton '24 합격생이 수질 센서 프로젝트를 잡은 방식이 이거다.
- **팁 3 — 5명 인터뷰 룰**: 아이디어를 확정하기 전 같은 문제를 겪는 사람 5명에게 10분씩 전화해라. "이 문제로 얼마나 불편하냐"고 직접 물어봐서 3명 이상이 "맞아"라고 하면 문제 실재성 확인 완료.
- **팁 4 — 1주일 선택 데드라인**: 아이디어 선택 기간을 캘린더에 7일 제한으로 블록해라. 완벽한 아이디어는 존재하지 않는다. 실행이 아이디어를 완성시킨다.
- **팁 5 — 국제학생 각도 극대화**: "내가 한국인이기 때문에 보이는 문제"를 먼저 써라. 문화·언어·이민 경험에서 나오는 마찰은 미국 학생이 절대 볼 수 없는 각도이며 사정관에게 즉각 눈에 띈다.
- **팁 6 — 아이디어 피칭 테스트**: 최종 후보 아이디어를 부모님이나 친구에게 30초로 설명했을 때 "그거 진짜 필요하겠다"가 나오면 문제 실재성 통과. "잘 모르겠다"가 나오면 문제 정의를 다시 해라.
- **팁 7 — 타인의 문제 vs 내 문제**: Harvard 합격생 서사 분석 결과, 에세이 설득력은 "내가 직접 겪은 문제" 기반이 "타인을 돕기 위해 선택한 문제"보다 평균적으로 더 구체적이고 강하다. 가능하면 내 마찰을 출발점으로 삼아라.

# 강의 72 · 프로젝트 설계 캔버스

**원리: 캔버스 없이 시작 = 3개월 뒤 "방향을 잃었다"**

```
프로젝트 설계 캔버스 = 4개 블록
┌──────────────┬──────────────┐
│  목표 (Goal) │  범위 (Scope)│
├──────────────┼──────────────┤
│ 일정(Timeline│ 산출물(Output│
└──────────────┴──────────────┘
```

각 블록을 1페이지 이내로 **먼저 채운 후** 실행 시작.

🎓 **Ivy Tip**: 캔버스는 A3 1장으로 출력해 책상 위에 붙여라. 매주 월요일 30초 보는 것만으로도 방향감을 유지할 수 있다. Columbia '25 합격생 김민준이 실제로 한 방법이다.

# 72-1. 캔버스 블록 1 · 목표 (Goal)

**좋은 목표의 조건 — SMART+W**

| 요소 | 설명 | 나쁜 예 | 좋은 예 |
|---|---|---|---|
| **S** pecific | 구체적 | "앱을 만든다" | "iOS 앱 v1 출시" |
| **M** easurable | 측정 가능 | "사람들이 쓴다" | "월 50 active users" |
| **A** chievable | 현실적 | "전국 배포" | "학교 내 30명 파일럿" |
| **R** elevant | 스파이크와 연결 | "이 분야 관심 있음" | "컴퓨터과학 스파이크 직결" |
| **T** ime-bound | 기한 명확 | "내년 어느 시점" | "2026년 3월 31일까지" |
| **W** hy | 내적 이유 | (없음) | "내가 직접 겪은 이 문제를 끝내겠다" |

✍️ **실습**: 내 프로젝트 목표를 SMART+W로 1문장씩 작성.

🎓 **Ivy Tip**: W(Why) 항목은 에세이 첫 문장이 된다. 강렬한 이유 한 줄이 없으면 목표를 다시 써라.

---

# 72-2. 캔버스 블록 2 · 범위 (Scope)

**핵심 개념: MVP (Minimum Viable Product / Minimum Viable Project)**

```
처음 생각한 범위 (WANT)
  ├─ 앱: iOS + Android + 웹
  ├─ 기능: 매칭 + 채팅 + 결제 + 리뷰
  └─ 사용자: 전국 고등학생

MVP 범위 (NEED to finish)
  ├─ 플랫폼: 웹 only (Notion/Airtable 기반)
  ├─ 기능: 프로필 등록 + 이메일 연결
  └─ 사용자: 학교 국제학생 30명 파일럿
```

🎓 **Ivy Tip 1**: Stanford d.school 교수가 말한 "Scope it down until it's embarrassingly small — then ship it." 작게 완성하는 게 크게 미완성보다 100배 낫다.

🎓 **Ivy Tip 2**: MVP를 정하는 기준 — "이것 하나만 작동하면 누군가의 문제를 해결하는가?" YES이면 그게 MVP다. 나머지는 v2로 미뤄라.

---

# 72-2b. 범위 결정 — 실전 컷 기준

**"넣을까 뺄까" 결정 기준표**

| 기능/요소 | 넣기 기준 | 빼기 기준 |
|---|---|---|
| 핵심 기능 | MVP 없이 문제 해결 불가 | 있으면 좋지만 없어도 됨 |
| 플랫폼 | 타깃 사용자가 가장 많이 쓰는 것 1개 | 추가 플랫폼은 v2 |
| 사용자 규모 | 직접 섭외 가능한 숫자 | "전국", "수천 명"은 v2 |
| 새 기술 습득 | 1–2개 이내 | 3개 이상 새 기술 = 범위 과다 |

🎓 **Ivy Tip 1**: Airtable + Tally.so + Zapier 조합으로 매칭 플랫폼 MVP를 **2주 안에** 만든 사례가 여럿이다. 코딩 없이도 작동하는 범위가 최고의 MVP다.

🎓 **Ivy Tip 2**: "이걸 빼면 프로젝트가 죽는가?" NO이면 빼라. 처음 범위의 60%를 쳐내야 6개월 안에 완성할 수 있다.

🎓 **Ivy Tip 3**: Yale '25 합격생 이소연(뉴저지) — "처음엔 앱 개발 계획이었는데 Webflow+Airtable로 바꿨다. 결국 더 빨리 런칭했고 에세이 소재가 됐다."

# 72-3. 캔버스 블록 3 · 일정 (Timeline)

**6개월 기본 프레임**

| 단계 | 기간 | 핵심 활동 | 체크포인트 |
|---|---|---|---|
| **리서치** | M1 | 문제 인터뷰 5명+, 시장 조사 | 인터뷰 노트 |
| **설계** | M1–M2 | 와이어프레임/기획서 | 설계 문서 v1 |
| **빌드 v1** | M2–M4 | 핵심 기능 구현 | 작동하는 MVP |

🎓 **Ivy Tip**: 시험 기간(AP, SAT, 기말)을 미리 표시하고 해당 2주는 "유지 모드"로 설정해라. 계획에 시험 기간이 없으면 반드시 무너진다.

# 72-4. 캔버스 블록 4 · 산출물 (Output)

**산출물 = "원서 마감일에 링크/파일로 첨부할 수 있는 것"**

| 프로젝트 유형 | 산출물 예시 | 첨부 방식 |
|---|---|---|
| 소프트웨어 | GitHub repo + 배포 URL + 사용자 수 스크린샷 | Activity list URL |
| 연구 | 논문 초고 + 데이터셋 + 발표 슬라이드 | 추가 파일 업로드 |
| 비영리 | 웹사이트 + 참가자 명단 + 이벤트 사진 | 링크 + 포트폴리오 PDF |
| 미디어 | 발행된 매거진/뉴스레터 아카이브 링크 | URL |
| 커뮤니티 | 멤버 수 + 미팅 로그 + 임팩트 요약 1장 | PDF 1장 |

✍️ **실습**: 내 프로젝트의 산출물 3개를 지금 적어라. 원서에 첨부할 링크를 상상하며.

🎓 **Ivy Tip**: 산출물에 숫자를 넣어라. "앱 만들었음"보다 "월간 활성 사용자 87명, 누적 세션 340회"가 10배 설득력 있다. Day 1부터 숫자 추적 습관을 만들어라.

# 72-6. 🎓 실전 꿀팁 모음 (강의 72)

- **팁 1 — 목표 숫자는 현실보다 30% 보수적으로**: "월 200명 목표" → "월 60명 목표"로 잡아라. 초과 달성이 에세이 서사에서 훨씬 강하다. MIT '24 합격생 장현우는 50명 목표 → 130명 달성 서사로 에세이를 썼다.
- **팁 2 — MVP 범위 결정에 24시간 제한**: 범위 논의에 1주일 쓰는 학생이 많다. 24시간 안에 "핵심 기능 3개"를 정하고 나머지는 전부 v2로 미뤄라.
- **팁 3 — 노코드 우선 검토**: Webflow, Bubble, Airtable, Glide, Tally.so, Notion Sites — 이 6개 툴로 대부분의 MVP는 2~3주 안에 만들 수 있다. 코딩 배우는 데 2개월 쓰는 것보다 노코드로 1개월 안에 런칭하는 게 낫다.
- **팁 4 — 일정에 "버퍼 주(Buffer Week)" 삽입**: 각 마일스톤 사이에 1주일 버퍼를 넣어라. 계획은 항상 예상보다 1.5배 걸린다. 버퍼 없는 간트는 첫 달부터 무너진다.
- **팁 5 — 산출물 링크를 Day 1에 만들어라**: GitHub 레포, Notion 페이지, 웹사이트 URL — 아무것도 없어도 Day 1에 빈 페이지를 만들어라. 링크가 있으면 채워야 한다는 압박이 실행 동력이 된다.
- **팁 6 — 숫자 추적 습관**: Google Sheets에 "날짜 / 오늘 뭘 했나 / 숫자 지표" 3열 표를 만들어 매일 30초씩 채워라. 원서 작성 시 이 시트가 에세이의 구체적 숫자 소스가 된다.
- **팁 7 — 캔버스 공유**: 멘토나 InHero 서클 멤버 1명과 캔버스를 공유하고 매월 리뷰를 약속해라. 혼자 보는 캔버스보다 10배 실행력이 높다.

# 강의 73 · 실행 계획

**원리: 계획 없는 실행 = 3개월 후 "어디까지 했더라?"**

```
실행 계획 = 마일스톤 + 주간 액션 + 간트 초안
```

**마일스톤 정의**
- 마일스톤 = **"멈춰 서서 확인하는 체크포인트"**
- 월 1회, 총 6개 (시작 + 중간 4 + 완성)
- 각 마일스톤에 **명확한 완료 기준(Done Criteria)** 필요

🎓 **Ivy Tip**: 마일스톤 완료 기준(Done Criteria)을 "했다"가 아닌 **숫자나 산출물로** 정의하라. "인터뷰 완료" → "인터뷰 노트 5개, 공통 문제 3개 추출 완료"처럼.

# 73-1. 마일스톤 설계 — 6단계 템플릿

| 마일스톤 | 시점 | 완료 기준 (Done Criteria) | 산출물 |
|---|---|---|---|
| **M0** 킥오프 | Week 1 | 캔버스 완성, 팀/멘토 확정 | 캔버스 1장 |
| **M1** 문제 검증 | Month 1 | 인터뷰 5명+, 핵심 문제 1개 확정 | 인터뷰 노트 |
| **M2** 설계 완료 | Month 2 | 와이어프레임/기획 v1 완성 | 설계 문서 |
| **M3** MVP 빌드 | Month 4 | 핵심 기능 작동, 내부 테스트 | 작동 버전 |
| **M4** 파일럿 완료 | Month 5 | 실제 사용자 5–30명 피드백 | 피드백 정리 |
| **M5** 공개 런칭 | Month 6 | 산출물 공개, 문서화 완료 | 최종 결과물 |

✍️ **실습**: 내 프로젝트에 맞게 각 Done Criteria를 구체적으로 채워라.

# 73-3. 주간 액션 루프

**"프로젝트는 주간 루프로 산다"**

```
매주 일요일 밤 (30분)
  ┌─ 지난 주 체크: 계획 vs 실제 → 갭 파악
  ├─ 이번 주 액션 3개: "화요일까지 A, 목요일까지 B, 금요일까지 C"
  └─ 블로커 1개: 막히는 것 → 멘토/팀원에게 월요일 질문
```

| 주간 루프 항목 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 목표 | "코딩 열심히 한다" | "로그인 기능 구현 완료" |
| 시간 | "될 때 한다" | "화·목 8–10pm 고정" |
| 블로커 | 혼자 며칠 고민 | 48시간 내 도움 요청 |

🎓 **Ivy Tip**: Yale '24 합격생의 말 — "주간 루프 없으면 6개월이 눈 깜짝할 새 지나간다. 30분 리뷰가 프로젝트를 살렸다."

# 73-6. 흔한 실수 ❌ + FAQ

**❌ 흔한 실수**
- 월간 계획 세우고 **주간 루프 없음** → 한 달 뒤 아무것도 안 됨
- Done Criteria 없음 → "어느 정도 됐나?"를 스스로 모름
- 간트를 한 번 세우고 **업데이트 안 함** → 현실과 괴리
- 프로젝트와 학교 시험이 겹칠 때 **둘 다 포기** → 시험 기간엔 액션 하나로 줄이고 유지

**Q. 계획이 자꾸 바뀌면 어떡하나요?**
A. 정상이다. 계획을 **"맞추는 것"** 이 목표가 아니라, **"어긋난 이유를 파악하고 재조정"** 하는 것이 목표다. 매주 루프에서 갱신하면 된다.

**Q. 혼자 하는데 멘토가 없으면?**
A. InHero 멘토 세션 + 같은 프로젝트 하는 서클 멤버를 "가짜 팀장"으로 삼아 주간 체크인하라.

# 73-7. 🎓 실전 꿀팁 모음 (강의 73)

- **팁 1 — 블로커 48시간 룰**: 막히면 48시간 이상 혼자 고민하지 마라. 48시간이 지나도 해결 안 되면 멘토/서클/포럼에 질문해라. 혼자 1주일 막히는 것이 프로젝트를 죽이는 1순위 원인이다.
- **팁 2 — 시험 기간 유지 모드**: AP 시험, SAT, 기말 기간에는 "액션 1개"만 유지해라. 완전히 멈추면 재시작 비용이 너무 크다. 주 1시간이라도 유지하면 모멘텀이 살아있다.
- **팁 3 — 마일스톤 달성 시 자축**: M1 달성 → 좋아하는 음식 먹기, M3 달성 → 하루 쉬기. 보상 없는 6개월 마라톤은 번아웃으로 끝난다. Brown '25 합격생 서클이 마일스톤마다 온라인 파티를 열었다.
- **팁 4 — 실패 로그도 기록해라**: "이번 주 뭘 못 했고 왜 못 했나"를 솔직하게 기록해라. 이 실패 로그가 에세이의 "역경을 어떻게 극복했나" 문항의 소재가 된다. Harvard는 실패를 숨기는 지원자보다 직면하고 배운 지원자를 원한다.
- **팁 5 — 주간 지표 1개 고정**: 매주 추적할 숫자 하나를 정해라. (사용자 수, 인터뷰 수, 뉴스레터 구독자, GitHub 커밋 수 등) 숫자가 올라가면 동기가 생기고, 내려가면 원인을 찾게 된다.
- **팁 6 — 공개 런칭 날짜를 미리 공유해라**: "나 X월 X일에 런칭한다"고 서클에 선언해라. 공개 약속이 있으면 마감을 지킬 확률이 극적으로 올라간다. 이건 스타트업 창업자들이 쓰는 "공개 커밋" 전략과 동일하다.
- **팁 7 — 간트를 매월 1회 업데이트**: 간트는 계획이지 법이 아니다. 매월 첫째 주 일요일에 간트를 현실에 맞게 수정해라. 수정된 간트가 원래 간트보다 더 유용하다.

**Q. 원서 마감까지 6개월도 안 남았어요.**
A. 타임라인을 3–4개월로 압축하고 범위를 더 줄여라. **"작은 것의 완성"** 이 항상 정답.

**Q. 프로젝트를 두 개 동시에 해도 되나요?**
A. 안 된다. 하나에 집중해서 완성해라. 두 개 미완성보다 한 개 완성이 원서에서 훨씬 강하다.
